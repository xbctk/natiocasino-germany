# AGENTS.md

## 1. Назначение документа

Этот файл задаёт обязательные рабочие правила для всех разработчиков и AI-агентов, которые продолжают проект National Casino New Zealand.

Главный источник требований проекта — `docs/ТЗ.md`. Перед изменением структуры, дизайна, контента или поведения интерфейса необходимо прочитать относящиеся к задаче разделы ТЗ. Этот файл не заменяет ТЗ, а определяет порядок работы с ним.

Если запрос пользователя противоречит текущему ТЗ, выполнить последнее прямое указание пользователя и в той же задаче синхронизировать соответствующий раздел `docs/ТЗ.md`.

## 2. Описание проекта

National Casino New Zealand — обзорный партнёрский сайт бренда казино и беттинга для аудитории Новой Зеландии.

Сайт должен:

- презентовать бренд National Casino;
- объяснять функции казино, слотов и спортивного беттинга;
- рассказывать о регистрации, использовании платформы, бонусах и приложении;
- показывать преимущества и недостатки бренда;
- быть понятным как опытным игрокам, так и новым пользователям.

Основной визуальный приоритет — премиальность, доверие и спокойная подача без визуального перегруза типичными казино-эффектами. Основной акцент контента — казино; беттинг является дополнительным направлением.

Целевой регион — Новая Зеландия. Язык интерфейса и контента — английский.

## 3. Страницы проекта

Основные страницы:

## 4. Источники и приоритет требований

Использовать следующий порядок приоритета:

1. Последнее прямое указание пользователя.
2. `docs/ТЗ.md` — структура, размеры, палитра, типографика, навигация, адаптивность, интерактивность и прочие явные требования.
3. DOCX-файлы из папки `Тексты` — единственный источник редакционного текста и порядка контентных блоков.
4. Папка `Референсы` — только источник композиции и комбинации блоков, списков, таблиц и карточек.
5. `docs/source/Главная страница.pdf`, `.h2d`, скриншоты и оригинальный сайт — вспомогательные визуальные источники только для требований, уже зафиксированных в ТЗ, либо для прямой задачи по извлечению фирменного ассета.

Оригинальный сайт бренда: `https://natiocazino.com/`.

Не переносить новые решения с оригинального сайта или референсов автоматически. Сначала зафиксировать принятое решение в `docs/ТЗ.md`.

## 5. Правила контента

Редакционный текст разрешено брать только из:

- `Тексты/National Casino New Zealand Main Page.docx`;
- `Тексты/National Casino New Zealand Bonuses.docx`;
- `Тексты/National Casino New Zealand App.docx`.

Запрещено:

- придумывать, дополнять или переписывать редакционный текст;
- переводить или локализовать текст;
- проводить фактчекинг с последующим изменением текста;
- менять смысл, порядок абзацев, списков, таблиц и заголовков;
- объединять, разделять или переставлять утверждённые контентные блоки;
- создавать интерфейсные подписи, которых нет в ТЗ, кроме невидимых accessibility-атрибутов.

Строки `Meta title` и `Meta description` в каждом DOCX являются соответственно заголовком и описанием Hero соответствующей страницы.

Главная страница содержит ровно 20 контентных блоков в порядке, закреплённом в `docs/ТЗ.md`. Hero, header, sidebar и footer в эти 20 блоков не входят.

## 6. Технологический стек

- Next.js с App Router;
- React;
- TypeScript в строгом режиме;
- Tailwind CSS через PostCSS;
- обычный CSS в `app/globals.css` для текущей дизайн-системы и компонентов;
- HTML и минимально необходимый клиентский JavaScript.

Менеджер пакетов — `pnpm`. Версии зависимостей определяются `package.json` и `pnpm-lock.yaml`; lock-файл является источником истины для воспроизводимой установки.

Не менять утверждённый технологический стек без предварительного согласования с пользователем.

Не добавлять новую библиотеку, UI-kit, state manager, CSS-in-JS или backend-зависимость без реальной необходимости и отдельного согласования.

## 7. Команды проекта

Установка зависимостей:

```bash
pnpm install
```

Запуск разработки:

```bash
pnpm dev
```

Сайт по умолчанию доступен по адресу `http://localhost:3000`.

Проверка ESLint:

```bash
pnpm lint
```

Production-сборка:

```bash
pnpm build
```

Запуск собранной версии:

```bash
pnpm start
```

Не считать задачу завершённой, если затронутый код не прошёл как минимум ESLint и production build. Если проверка невозможна по внешней причине, явно сообщить об этом.

```text
app/

  Hero.tsx             Общий Hero
  MainContent.tsx      Контентные блоки Main
  PlaceholderMedia.tsx Серые области будущих изображений
  Footer.tsx           Общий footer

  footer/              Оригинальные графические ассеты footer

  source/              Исходный PDF-макет и дизайн-файлы
```

Новые файлы размещать по назначению:

- компоненты — в `components`;
- маршруты и page/layout-файлы — в `app`;
- статические ассеты — в тематической подпапке `public`;
- техническую и проектную документацию — в `docs`;
- временные файлы — только в `tmp`, с удалением после завершения задачи.

Не складывать рабочие файлы хаотично в корень. Не перемещать уже организованные пользовательские материалы без прямой необходимости.

## 9. Архитектура и код

- Использовать переиспользуемые компоненты для общих и повторяющихся элементов.
- По умолчанию использовать Server Components. Добавлять `"use client"` только при наличии реальной интерактивности или browser API.
- Не переносить весь экран в один клиентский компонент.
- Сохранять строгую типизацию; не использовать `any` без обоснованной причины.
- Предпочитать семантические элементы HTML.
- Все интерактивные элементы должны работать с клавиатуры и иметь видимый `focus-visible`.
- Декоративные изображения и SVG должны быть скрыты от accessibility tree.
- Содержательные изображения должны иметь корректный `alt`.
- Использовать `next/image` для растровых изображений, когда это не мешает конкретному техническому сценарию.
- Не добавлять ненужный клиентский JavaScript, сложные абстракции или преждевременную универсализацию.
- Не подключать backend, авторизацию, аналитику, платёжные системы и внешние интеграции без отдельного запроса.

## 11. Header

- Header закреплён сверху при прокрутке.
- Слева располагается логотип.
- Desktop-навигация Main, Bonuses и App начинается по сетке у левой границы внутренней области контента.
- Между пунктами desktop-навигации используются декоративные золотые ромбы с короткими линиями.
- Справа порядок элементов: `Log In`, `Register now`, круглый флаг Новой Зеландии и `NZ`.
- `Register now` — основной CTA, `Log In` — вторичная кнопка.
- Индикатор `NZ` не является переключателем языка и не содержит стрелки.
- На tablet/mobile используется компактный официальный логотип и раскрываемое мобильное меню.

Официальные ассеты находятся в `public/brand`. Не пересобирать логотип или флаг средствами CSS.

## 12. Sidebar

- Постоянный sidebar показывается только на desktop.
- Sidebar закрепляется под header и имеет собственную вертикальную прокрутку при необходимости.
- На tablet/mobile он заменяется компактным меню якорных разделов.
- Платформенный блок и редакционная навигация `Navigation` являются разными элементами.
- `Navigation` раскрывается и закрывается; её пункты имеют отступ `8px`, не содержат порядковых чисел и отражают активную секцию.
- Платформенный список содержит: `Games`, `Live dealers`, `Sports betting`, `Live betting`, `Promotions`, `Tournaments`, `Hall of fame`, `VIP`.
- Пункт `Support` не отображается.
- `Games` и `Live dealers` не раскрываются и не имеют стрелок.
- У `Promotions` badge `14`, у `Tournaments` badge `3`.
- Карточки `Fortune wheel`, `Missions` и `Application` используют локальные оригинальные ассеты из `public/sidebar`.
- Карточка `Application` является зафиксированным исключением из правила серых заглушек и использует `public/sidebar/application.png`.

## 13. Компоновка контентных блоков

- Небольшой список: desktop-композиция `50/50`, список слева, изображение справа.
- Заголовок и 2-3 небольших абзаца: изображение заполняет блок; текст располагается слева примерно на половине ширины; будущая визуальная композиция — справа; поверх изображения используется затемняющий градиент.
- Таблица: отдельная строка на `100%` ширины контентного контейнера.
- В блоках с таблицами или оформленными списками обычный текст растягивается на всю доступную ширину.
- Ограничение ширины текста сохраняется в блоках, где изображение заполняет всю секцию и текст располагается поверх него.
- На tablet/mobile двухколоночные композиции перестраиваются в одну колонку без изменения порядка текста.

Таблицы могут иметь локальный горизонтальный скролл внутри собственного контейнера. Горизонтальный скролл всей страницы запрещён.

## 14. Изображения

- До отдельного финального этапа не генерировать и не подбирать новые контентные изображения.
- Места будущих изображений заполнять цветом `#757575` с сохранением финальных размеров, пропорций и скруглений.
- Исключения допускаются только для уже утверждённых фирменных ассетов, явно перечисленных в ТЗ.
- Не использовать изображения, визуально имитирующие кнопки или другие элементы управления.
- Не загружать изображения напрямую с внешнего домена в runtime, если можно сохранить утверждённый ассет локально.
- Не заменять существующий утверждённый ассет новым вариантом без прямого запроса.

## 15. Интерактивность

- Кликабельными являются только явно оформленные кнопки и ссылки навигации.
- Карточки и поверхности блоков не делать кликабельными.
- CTA пока могут не иметь финального URL, если сценарий не определён в ТЗ.
- Не придумывать поведение кнопок, формы или интеграции.
- Якорная навигация должна учитывать высоту sticky-header и `prefers-reduced-motion`.

## 16. Адаптивность

При любых изменениях интерфейса сохранять существующую адаптивность и не ухудшать поведение уже реализованных экранов.

Обязательно проверять как минимум:

- desktop около `1728px`;
- распространённый laptop/desktop около `1280px`;
- tablet около `768px`;
- mobile около `390px`.

Проверять:

- отсутствие горизонтального скролла страницы;
- переключение desktop и mobile-навигации;
- отсутствие перекрытий sticky-header;
- читаемость и отсутствие обрезания текста;
- адаптивность изображений и серых заглушек;
- доступность всех кнопок и ссылок;
- поведение широких таблиц внутри локального scroll-контейнера.

## 17. Git

Git-репозиторий может быть не инициализирован. Не выполнять `git init` без прямого запроса пользователя.

Если Git доступен:

- перед работой проверять `git status --short`;
- считать существующие незакоммиченные изменения пользовательскими и сохранять их;
- не откатывать и не перезаписывать несвязанные изменения;
- не использовать `git reset --hard`, `git clean -fd`, force push и другие разрушительные команды;
- не выполнять `git checkout -- <file>` или аналогичный откат без явного разрешения;
- после каждой успешной задачи, изменившей файлы, по умолчанию создавать атомарный commit и отправлять текущую ветку в настроенный remote, если пользователь прямо не попросил не делать этого;
- при запрошенном commit включать только относящиеся к задаче файлы и использовать понятное атомарное сообщение;
- не изменять lock-файл без изменения зависимостей;
- не добавлять в Git `.next`, `node_modules`, временные файлы, логи, секреты и локальные конфигурации окружения.

## 19. Проверка результата

После каждого изменения выполнять проверки пропорционально задаче.

Минимальная техническая проверка:

```bash
pnpm lint
pnpm build
```

Для изменений интерфейса дополнительно:

1. Запустить `pnpm dev`.
2. Открыть изменённую страницу в браузере.
3. Проверить desktop, tablet и mobile.
4. Проверить клики, клавиатурный focus и раскрывающиеся элементы.

6. Проверить переполнение текста и отсутствие горизонтального скролла.

8. Сверить структуру и содержимое с `docs/ТЗ.md` и соответствующим DOCX.

Не исправлять несвязанные проблемы без запроса. Если во время проверки найдена критичная проблема, относящаяся к сделанному изменению, исправить её и повторить проверки.
